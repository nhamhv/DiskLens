# Architecture

DiskLens has two parts that talk through Tauri commands and events:

- a **Rust backend** that does every filesystem operation;
- a **React frontend** that only renders what the backend sends.

```
┌──────────── React (src/) ────────────┐          ┌──────────── Rust (src-tauri/src/) ────────────┐
│ features/welcome   start screen      │ invoke() │ commands/scan.rs    scan, cache, browse tree   │
│ features/disk      treemap + sidebar │ ───────▶ │ commands/delete.rs  trash / permanent delete   │
│ features/apps      app list/details  │          │ commands/apps.rs    list, icons, sizes, update │
│ components/        shared UI         │ ◀─────── │ commands/system.rs  Finder, clipboard, FDA     │
│ lib/api.ts         typed invoke()    │  emit()  │ scanner.rs  cache.rs  apps.rs  state.rs        │
└──────────────────────────────────────┘          └────────────────────────────────────────────────┘
```

## Layout

| Path | What lives there |
|---|---|
| `src/App.tsx` | Picks which screen to show (welcome / disk / apps / dev). Holds the speed setting. |
| `src/features/disk/` | `DiskView` owns one scanned root: the scan lifecycle, navigation, deletes. It also contains `Treemap`, `Sidebar`, and `EntryMenu`, the right-click menu shared by both. |
| `src/features/apps/` | `AppsView` (list, search, sort, update check) and `AppDetails` (the side panel). |
| `src/features/dev/` | Developer cleanup. `DevView` (scan, tabs, filters, quick-select, delete), `Rows`/`ItemRow`, `RulesView` (the in-app rules editor), `model.ts` (filtering and selection helpers), `jsonc.ts` (edits the rules file as text so comments survive). |
| `src/features/donate/` | Support screen. Donation links live in `links.ts`. Empty links are hidden. |
| `src/features/welcome/` | Start screen, previous scans, Full Disk Access notice, hidden space (purgeable + local snapshots). |
| `src/features/photos/` | `PhotosView`: blurry photos, screenshots and similar-shot groups, with lazy thumbnails. |
| `src/features/tray.ts` | The menu bar / tray icon. Built from JS so its labels follow the app language. |
| `src/components/` | Shared pieces: `DeleteDialog`, `SpeedPicker`, `LanguagePicker`. `ui/` is generated by shadcn. Don't hand-edit it unless you have to. |
| `src/lib/` | `api.ts` (every backend call), `types.ts` (mirrors the Rust structs), `platform.ts` (which features this OS has, loaded before the first render), `format.ts`, `kinds.ts` (folder/file classification), `delete.ts`. |
| `src/i18n/` | i18next setup and one JSON file per language. |
| `src-tauri/src/lib.rs` | Registers the commands. Nothing else. |
| `src-tauri/src/state.rs` | `AppState` (the current scan tree), the `Speed` → thread-pool mapping, cache helpers. |
| `src-tauri/src/diagnostics.rs` | Opt-in launch count (Aptabase), crash logs written to disk, and the prefilled GitHub issue text. |
| `src-tauri/src/scanner.rs` | The parallel directory walker. |
| `src-tauri/src/cache.rs` | Saves and loads scan results. |
| `src-tauri/src/platform/` | Everything OS-specific: `mod.rs` (shared types, `statvfs`), `macos.rs`, `linux.rs`. Each OS file exposes the same functions. |
| `src-tauri/src/apps.rs` | Finds installed apps, their data folders and their updates. macOS only. |
| `src-tauri/src/photos.rs` | Photo analysis: blur score (Laplacian variance), screenshot detection, perceptual hash (dHash) grouping. |
| `src-tauri/src/dev/` | Developer cleanup: `rules.rs` (catalog loading, merging, validation, path expansion), `walk.rs` (pruning project walker), `git.rs` (check-ignore, worktree status/prune), `mod.rs` (the scan pipeline and report). |
| `src-tauri/rules/` | `builtin.json` (the built-in catalog), `schema.json`, `template.jsonc` (starter for the user's file). |

## Platforms

All OS-specific code lives in `src-tauri/src/platform/`. `platform/mod.rs` re-exports `macos.rs` or `linux.rs`, so callers write `platform::trash_files()` and never use `cfg` themselves. A Windows port adds `windows.rs` with the same functions.

| Concern | macOS | Linux |
|---|---|---|
| Thread priority (`set_thread_priority`) | QoS class | `setpriority` nice + `ioprio_set` |
| Scanning `/` (`root_scan`) | adds the Data volume, skips APFS magic folders | adds local disk partitions from `/proc/self/mounts`, skips virtual and removable mounts |
| Trash (`trash_files`, `trash_info`) | `~/.Trash` | `$XDG_DATA_HOME/Trash/files`; deleting an item also removes its `.trashinfo` |
| Images (`thumbnail_gray`, `thumbnail_jpeg`) | ImageIO (reads HEIC) | the `image` crate (no HEIC) |
| Quick Look, hidden space, Full Disk Access, Applications | yes | stubs that return "unsupported" |

`platform_features` tells the UI which of these exist; `src/lib/platform.ts` loads it before the first render and screens hide what the OS lacks. Opening files, revealing them and the clipboard go through the Tauri opener/clipboard plugins, which already work on every OS. Classification rules and `builtin.json` list paths for both OSes; paths that don't exist are harmless.

## Scanning

- **Directory walk.**
  - `scanner::scan_root` walks a folder with rayon: one task per subdirectory.
  - Sizes come from `lstat` *allocated blocks*, not file length. This makes sparse files and APFS clones report what they really use.
  - It never follows symlinks.
  - It stays on one device, so `/System/Volumes/Data` and network mounts aren't counted twice.
  - Hard links are counted once.
  - Scanning `/` also skips the APFS magic folders `/.vol`, `/.nofollow` and `/.resolve`, which can expose the same files again by inode or path.
  - Code bundles (`.app`, `.framework`, `.appex`, …; see `classify::BUNDLES`) are sized but their children are dropped, so a scan of `/` doesn't store hundreds of thousands of nodes for bundle internals. Opening one in the UI (`collapsed: true`) rescans just that folder. Largest Files therefore doesn't see files inside bundles until they're opened.
- **Speed modes.** `Speed` picks the thread count and the thread priority (macOS QoS class; on Linux `nice` 19 + idle I/O for Low, `nice` 10 for Balanced).
  - **Low:** 2 threads at `QOS_CLASS_BACKGROUND`. The kernel keeps them on efficiency cores and throttles their I/O.
  - **Balanced:** half the cores at `UTILITY`.
  - **Fast:** 2× the cores at `USER_INITIATED`. This mode oversubscribes the cores because the walk is I/O-bound.
- **Live updates.** While scanning, the backend emits:
  - `scan-progress` every 200 ms;
  - `scan-entry` as each top-level child finishes, so the treemap fills in live;
  - `scan-done` at the end.
- **Cancelling.** A new scan cancels the old one through an `AtomicBool`. The finished tree is only stored if it was not cancelled, and that check happens under the lock.
- **The tree stays in Rust.** The UI asks for one folder at a time (`list_children`, capped at 300 entries plus an "other" bucket). It also asks for the largest files under a folder (`largest_files`, a bounded min-heap).
- **Browsing during a scan.** Each top-level folder is moved into `ScanCtx::done` as soon as it is fully sized, before its `scan-entry` is sent. `AppState::with_node` reads from there until the full tree is stored, so those folders can be opened right away. Deletes and rescans stay blocked until `scan-done`: in the UI (`locked`), and in `delete_paths` for anything under the scanning root. Otherwise the finished tree would bring deleted items back.
- **Rescan Folder.** This rescans one subtree and splices it into the stored tree.
- **Comparing scans.** A new scan of the same root keeps the previous tree, pruned to items of at least `PREV_MIN`, as `ScanTree::prev` (also saved in the cache). `list_children` returns each child's `delta` and the folder's `prevSize`; `scan_changes` lists the biggest changes, descending into a folder only when its children explain most of its change.
- **Old files.** `largest_files` takes an optional `modified_before`, used by the "untouched for 1 year+" filter.

## Photos

`photos_scan` walks the chosen folders (skipping hidden folders, bundles and photo libraries), then on the speed-mode pool decodes a 256 px grayscale thumbnail of each image. From it, it computes a blur score (variance of the Laplacian; only for camera formats, since flat screenshots always look "blurry") and a 64-bit dHash. Screenshots are found by name, plus Spotlight's `kMDItemIsScreenCapture` on macOS. Similar photos are grouped greedily by Hamming distance within the same aspect ratio; the sharpest, largest one comes first and is the one to keep. Deleting goes through `delete_paths` like everything else.

## Safety and categories

`classify.rs` gives every path a category (system, caches, appData, media, …) and a safety level: `safe`, `review`, `risky` or `unknown`. It goes by path, not by folder name:

- Rules are checked for each ancestor from the scan root down. The first *fixed* match decides the whole subtree, so `/System/Library/Caches` stays risky and `~/Library/Caches/x` stays safe.
- System locations are checked first, and `safe` is an allowlist: user caches and logs, the Trash, a few package-manager caches and dev junk (`node_modules`, `__pycache__`, `DerivedData`, …).
- Comparisons are lowercase, because the default macOS filesystem is case-insensitive.
- `Classifier::step` is the only place that turns a parent's class into a child's class. `list_children`, `largest_files` and `scan_summary` all use it, so the treemap, sidebar and summary always agree.

`scan_summary` walks the subtree under the current folder. It totals sizes by category and by safety, and lists the safe items to clean (at most `CLEANUP_LIMIT`, excluding the Trash, which the start screen already offers to empty). The UI asks for it only while the Cleanup or Summary tab is open.

## Cache

After each scan, the tree is saved with bincode to the app cache directory: `~/Library/Caches/com.nhamhv.disklens/`. Next to each file there is a small JSON sidecar. The start screen can list previous scans by reading only the sidecars.

Where the tree goes depends on `CacheMode` (set from the start screen through `set_cache_mode`): `disk`, `memory`, or `auto`. `auto` saves to disk unless the volume would be left with under 1 GiB free (`cache::low_on_space`), then keeps the encoded tree in `AppState::mem_caches` (newest 3, lost when the app closes). A failed disk write falls back to memory too, and the stale disk copy of that root is removed to free space. `state::cached_tree`, `cached_node`, `list_caches`, `forget_cache` and `clear_caches` look in both places; memory entries have `inMemory: true` in `ScanMeta`.

When a delete or rescan edits the tree, a background thread re-saves it. A mutex keeps two saves from writing at the same time.

## Deleting

`delete_paths(paths, permanent)` works like this:

1. It sorts the paths and drops any that sit inside another selected folder.
2. It refuses protected paths (`is_protected`):
   - `/`, `/System`, `/usr` (except `/usr/local`), `/Applications` itself;
   - `~` and its standard folders (Desktop, Documents, Downloads, Library…);
   - anything relative or containing `..`.
3. It moves each path to the Trash (`trash` crate) or removes it, then removes it from the scan tree.
4. It returns, per item, what was deleted and what failed.

The confirmation is enforced in the UI (`DeleteDialog`):

- Trash takes one step.
- Permanent delete takes two.
- **Cancel** holds focus, so pressing Enter can never delete anything.

## Applications

- **Finding apps.** `apps::list` reads the `Info.plist` of each bundle in `/Applications` and `~/Applications`, two levels deep.
- **Last used.** One `mdls` call gets `kMDItemLastUsedDate` for all apps at once.
- **Icons.** `NSWorkspace iconForFile` renders each icon to PNG through objc2. The result is cached on disk, keyed by bundle path and mtime.
- **Data folders.** These are matched **only** by exact bundle id, or by exact app name for a few folders. This is why "Reset app data" can never touch another app's files.
- **Update checks.**
  - App Store apps (those with a `_MASReceipt`) are checked against the iTunes lookup API.
  - Sparkle apps are checked against their `SUFeedURL` appcast.
  - Everything goes through `curl` with a 10 s timeout.

## Developer cleanup

- **Rules.** `rules/builtin.json` is compiled in. The user's `~/.config/disklens/rules.json` (JSON with comments) is merged over it **by `id`**: a built-in id only changes the fields it sets (`"disabled": true` turns it off), a new id adds a rule marked `custom`. A broken file never stops a scan; problems come back as warnings with line and column.
- **Rule types.** `artifact` (folders inside projects, next to a marker file, optionally only if git ignores them), `location` (fixed paths; `~`, `$VAR`, `{bin:tool}`, `*`), `versioned` (keep the newest `keep` of each version group), `template` (a shared layout such as `vscode` applied per path). Any folder with a `CACHEDIR.TAG` is a generic cache.
- **Scan.** Fixed locations first, then a parallel walk of the chosen folders that never descends into a match or into `skipNames`/`skipPaths`, then `git check-ignore` for `gitIgnored` rules, then measuring. Items are deduplicated (nested ones dropped) and grouped by project root; `.git` files mark worktrees.
- **Safety.** Every item is `safe`, `rebuild` (with a `restore` command) or `caution`. Quick-select never picks `caution` or custom items. Items whose app is running, and custom locations outside `~`, can't be selected. Deleting goes through `delete_paths`; deleted worktrees are pruned from their main repo.
- **Editing rules.** `RulesView` edits the file in the app. Every keystroke is validated (debounced) by `dev_rules_check`, which runs the same loader a scan uses, plus checks for unknown top-level keys, `version` and duplicate ids. `dev_rules_save` refuses invalid text and refuses to overwrite if the file's mtime changed since it was read (the UI then offers "use the file's version" or "keep mine"). Writes go to a temp file that is renamed over. The editor polls the mtime to pick up outside edits, and the results screen shows a "rules changed — rescan" banner.

## Frontend conventions

- Every user-visible string goes through `t()`. Rust error messages are still English, and are shown as they are.
- Kinds (`lib/kinds.ts`) decide a tile's icon and its colour in "colour by type" mode. The kind `id` is also the translation key under `kinds.*`. The "safe to clean" hint and "colour by safety" mode use the backend's `safety` (`lib/safety.ts`).
- The treemap and bubbles views (`Treemap.tsx`, `Bubbles.tsx`) share `useTiles`, `useBox` and `Tooltip`. The chosen layout and colour mode are kept in localStorage.
- `lib/types.ts` must match the `#[serde(rename_all = "camelCase")]` structs in Rust.

## Diagnostics and privacy

`diagnostics.rs` does three things, all with paths scrubbed (`scrub` turns the home folder into `~` and other `/Users/x` or `/home/x` into `~user`):

- **Crash logs.** A panic hook, and errors thrown in the UI (`window.onerror`, unhandled rejections, sent through `log_ui_error`), write `crash-<time>-<kind>.log` to `<app data dir>/crashes/`. The newest 20 are kept. They are never sent anywhere. Native crashes (segfaults) are not caught.
- **Report a problem.** `ReportIssue` shows the text (version, OS, newest crash excerpt) and opens a prefilled GitHub issue; the user reads and submits it. `open_issue` only accepts the project's own issue URL.
- **Launch count.** One `app_open` event per launch to Aptabase, sent with `curl`, only after the user agreed (`StatsConsent`, stored in `telemetry.json` next to the crash folder). It carries the app version and OS, no id that persists, and never paths or scan data. The key is read at build time from `APTABASE_APP_KEY` (`APTABASE_HOST` for a self-hosted server). Builds without a key send nothing and never ask.
